Where the idea came from

Ollama and Lemonade did it first.
Hemera wanted more room.

Being honest about it: the concept is not new. Two servers shaped it, and hemera keeps what they got right. What it changes is who chooses the binaries — and how many you may keep.

Inspiration

Ollama

Made a local model one command away, and its API became the one every tool speaks.

  • Kept: the Ollama API, so ollama list / run / ps / stop work unchanged
  • Kept: models load on the first request and unload when idle
  • Kept: it reads ollama's own model store directly
Inspiration

Lemonade Server

Showed that one local OpenAI-compatible server can sit in front of several engines and pick the right one for the hardware — NPU included.

  • Kept: several engines behind one server
  • Kept: more than text — images and speech too
  • Kept: AMD hardware treated as first class, NPU included
Hemera adds

Flexibility, all the way down

Both choose the engine build for you. Hemera lets you choose — and keep more than one.

  • Any release of llama.cpp, side by side, pinned per model
  • Many binaries: sd.cpp, whisper.cpp, audio.cpp, ds4, ollama's fork, your own
  • Backend per model — ROCm, Vulkan, CUDA, CPU, NPU on one machine
  • A bridge to ComfyUI for models that exist only as workflows
  • Its own 3D API, where OpenAI defines none
  • Anthropic's API too, and remote providers as local names
Why bother? llama.cpp moves fast — on 2026-08-04 alone it shipped b10253, b10254 and b10255, each in a dozen platform variants. New architectures land almost immediately, but a build that ran your model perfectly yesterday can regress today, and a server that pins one bundled binary leaves you waiting for its next release either way. Hemera keeps every build you installed, so a regression costs one click, not a week.
Versions & backends

Update without fear.
Roll back in one click.

Engine releases install side by side under binary/<engine>/<version>/<variant>/. Updating never removes what worked.

  • A release browser in the Engines tab, filtered to the variants you track (ubuntu-rocm, ubuntu-vulkan-x64, …), with download progress and the full rollback history.
  • Pin per model: "engineVersion": "b10254" or "latest", and "engineVariant": "rocm".
  • One file, many models. A single GGUF becomes several names, each with its own context, offload, template, environment and engine.
  • GPU runtimes found for you. Hemera reads each binary's ELF headers, finds the ROCm, CUDA, oneAPI or OpenVINO libraries it needs, and warns when a build would silently fall back to CPU.

 All three dialects, translated

Three dialects, one port

Ollama, OpenAI and Anthropic APIs, with streaming, tool calls and reasoning translated across all three — which is what lets Claude Code drive a local GGUF.

Models say what they are

/v1/models carries a hemera object — kind, endpoint, typed parameters with ranges — and /api/tags adds image, video, 3d and speech to Ollama's capabilities.

Memory that is shared

Before anything loads, hemera estimates what it needs and unloads the longest-idle models — then ComfyUI's cache — only when memory is actually short.

Live audio goes first

Speech on the GPU freezes the LLMs for its few seconds; speech on the NPU freezes nothing. Requests marked background wait while a call is live.

Cancel actually frees the GPU

Close an image stream, delete a video or 3D job, and the work stops — not just the wait. Hung ComfyUI jobs are detected, restarted and retried once.

Files are never lost

ollama rm drops a configuration, not a file. Deleting a model file is a separate step that names every model it takes along and asks you to type the filename.

The ComfyUI bridge

Workflows in.
Model names out.

The newest 3D and video models ship as ComfyUI workflows long before anything else runs them. Hemera does not replace ComfyUI — it fronts it, over the same HTTP API ComfyUI's own page uses.

Point at it

Its folder (hemera starts and stops it) or the URL of one already running. Nothing is installed into ComfyUI.

Hemera looks

It asks ComfyUI which model files and nodes it has — including folders from extra_model_paths.yaml — every half minute.

Recipes match

A recipe names the files a family needs, the request parameters and the workflow. Each match is offered as a model under its file name.

Requests run

An OpenAI-shaped request fills the workflow, queues it, reports real progress, and returns the image, mp4 or .glb.

hemera.json — the whole setup
"comfyui": {
  "dir": "/opt/ComfyUI",          // folder with main.py
  // or: "url": "http://127.0.0.1:8188"
  "keepAliveSeconds": 300,     // then ask it to unload
  "stallSeconds": 900,         // silence = hung job
  "cancelSeconds": 15          // then kill to free GPU
}

  • Recipes from your own workflow. Export it with Save (API Format), press New recipe, and hemera drafts it: which inputs pick model files, which take prompt, seed, steps, size or image, and which node saves the result — ranges read from ComfyUI.
  • A form, not JSON. A live check of what each file pattern matches right now; any input of any node can become a client setting. Edit as JSON is there for the odd case.
  • Built-ins you can override. Edit one and it becomes yours; Revert brings the original back, Switch off hides it.
  • Memory per recipe. Each recipe says what one job needs at its peak (memoryMB), and hemera unloads idle models until it fits — ComfyUI's own free-memory reading misses what Vulkan engines hold.
  • Start, Restart, Stop from the Directories tab, with the exit code and last output when ComfyUI dies.

hemera's own endpoint

A 3D API
OpenAI never wrote.

The OpenAI specification has images, video and audio — but no 3D. So hemera defines /v1/3d/generations: image in, .glb out. It mirrors the Videos API on purpose — same job lifecycle, same status values — so one piece of client code drives both.

POST/v1/3d/generations
GET/v1/3d/generations/{id}
GET/v1/3d/generations/{id}/content
DELETE/v1/3d/generations/{id}
GET/v1/3d/generations
  • texture — vertex (minutes), pbr with base colour, metallic, roughness, normal and occlusion maps (tens of minutes), or none.
  • faces, texture_size, remove_background, seed — and every model publishes its own parameters with ranges in /v1/models.
  • Real progress 0–100, cancel with DELETE, and the parameters actually used come back for reproducibility.

Setup

From a jar to a model server
in five minutes.

Hemera runs on Linux x86-64 with a JDK 21 or newer. The reference machine is an AMD Ryzen AI Max+ 395 (Radeon 8060S, 128 GB, XDNA NPU) on Ubuntu — but nothing in it is vendor-specific.

01

What you need

Only a JDK to run hemera. The rest depends on what you want to serve.

  • JDK 21+ (OpenJDK is fine). No Maven, no Python, no containers.
  • A GPU runtime for your engines — Mesa/Vulkan drivers, ROCm, or CUDA. Hemera finds the libraries itself and tells you when one is missing.
  • ffmpeg on the PATH (optional) — for WebM/Ogg/M4A speech input and MP3/Opus/AAC speech output.
  • Model files — GGUFs anywhere on disk, or an existing ollama store.
02

Download and run

Config (hemera.json) and engine binaries live next to the jar unless you pass --home or set HEMERA_HOME.

shell
mkdir -p /opt/hemera && cd /opt/hemera
curl -LO https://github.com/peprasetya/hemera/releases/latest/download/hemera.jar
java -jar hemera.jar --port 12434      # [--home dir] [--log info|debug|trace]
03

Keep it running

The systemd unit in the repo sets OOMPolicy=continue: engines share hemera's cgroup, and an oversized model should cost that model, not the gateway. Hemera also marks engines as preferred OOM victims.

systemd
curl -L -o /etc/systemd/system/hemera.service \
  https://raw.githubusercontent.com/peprasetya/hemera/main/hemera.service
systemctl daemon-reload && systemctl enable --now hemera
journalctl -u hemera -f
04

Install engines, add models

Open http://host:12434/ — the configure UI. Plain HTML, no third-party assets, follows your OS theme, works on a phone.

  • Engines — pick a llama.cpp or stable-diffusion.cpp release and variant and install it. Install another one next to it any time. Add engine registers a binary you built yourself (ds4, whisper.cpp, audio.cpp, ollama's runner).
  • Directories — add model folders and ollama repositories; point hemera at ComfyUI.
  • Models — scanned files with projectors, MTP draft heads, VAEs and text encoders paired automatically. Configure a file as one or more named models; Load warms it now and reports any error.
  • Proxies — remote providers under local names. Voices — the voice library for speech.
05

Point your tools at it

Every client sees the same models. Hemera does not check API keys; put it behind your own proxy if it faces a network you do not trust.

clients
# Ollama CLI and anything that speaks Ollama
OLLAMA_HOST=host:12434 ollama list

# OpenAI SDKs
OPENAI_BASE_URL=http://host:12434/v1 OPENAI_API_KEY=local python app.py

# Claude Code on a local GGUF, through /v1/messages
ANTHROPIC_BASE_URL=http://host:12434 ANTHROPIC_AUTH_TOKEN=local \
  claude --model qwen3-coder
06

Bridge ComfyUI

Have a working ComfyUI with its custom nodes and model files (TRELLIS.2, Hunyuan3D, LTX…). Then tell hemera where it is — in the Directories tab or in hemera.json.

Its virtualenv is found as venv/ or .venv/ in or beside the folder; set python otherwise.

hemera.json
"comfyui": {
  "dir": "/opt/ComfyUI",
  "python": "/opt/ComfyUI/venv/bin/python",   // only if not found
  "args": [],                   // extra flags for main.py
  "autoStart": true,
  "memoryMB": 24576,           // fallback when a recipe has none
  "exclusiveGpu": false
}
07

Add speech (optional)

whisper.cpp publishes GPU builds only for Windows, so on Linux build it with Vulkan. audio.cpp runs on Vulkan, CPU, or — for Ryzen AI — the NPU; the same voice can be offered on both and the client chooses by name.

hemera.json
"engines": {
  "whisper.cpp":   { "binaryPath": "/opt/whisper.cpp/build/bin/whisper-server" },
  "audio.cpp":     { "binaryPath": "/opt/audio.cpp/build/audiocpp_server",
                     "defaultArgs": ["--backend", "vulkan"] },
  "audio.cpp-npu": { "binaryPath": "/opt/audio.cpp/build-npu/audiocpp_server",
                     "argStyle": "audiocpp", "healthPath": "/health",
                     "defaultArgs": ["--backend", "npu", "--threads", "2"] }
},
"models": [
  { "name": "whisper-large-v3-turbo", "engine": "whisper.cpp",

]
08

Or build it yourself

No build system: one javac and one jar call. The source is small enough to read in an afternoon.

shell
git clone https://github.com/peprasetya/hemera.git && cd hemera
./build.sh                    # -> hemera.jar
